# R2 流式 Git 入站（v0.16）

原生 HTTPS `git-receive-pack` 改用增量解析，不再把整个上传、所有展开对象和 delta 同时留在内存。Worker 仍只运行 JavaScript；服务端没有 Git 子进程、磁盘或容器。

## 持久化顺序

请求头有独立的 128 KiB/256 条命令预算。已知陈旧引用和禁止推送的引用在写入临时区之前拒绝，最终发布仍重新验证完整策略与引用。先把上传按最多 4 MiB 的块写入 R2 会话隔离区，读完请求体后再逐对象解析，避免大量细粒度 R2 写入阻塞上传连接。对象写入 `repos/<repo-id>/incoming/<session-id>/` 下的 R2 隔离区；未解析 delta 也存放在该会话中。解析器仅保留对象元数据和当前对象的字节，按需从隔离区或已有仓库读取基对象。临时对象和 delta 合并成目标大小 4 MiB、最多 1,024 项的块，大对象单独成块；会话内保留偏移索引，读取时复制单项并重新验证 Git SHA-1 或 delta 摘要。这样不会因缓存一个小对象而保留整个大块。

完整 pack SHA-1、尾部 EOF 和所有 delta 校验成功后，才把规范化对象分批保存至正式 R2 对象键。随后使用已有 DO 对象索引验证可达闭包与写入策略，最后发布引用。正式对象成功写入后保留至多 4,096 项、16,384 条边的会话内元数据；对象索引使用这些已持久化信息，减少重新读取刚写入对象的请求。缓存不保存文件内容，不绕过子对象存在性、类型、可达性或引用授权检查；重启或超出缓存预算时继续从 R2 验证。条件写入和完整内容校验继续防止覆盖冲突对象。校验失败、缺失 delta、暂存失败都不能发布引用；正式保存或策略验证的后续失败可能留下不可达对象，与已有存储模型一致，不宣称具备完整不可达对象 GC。

隔离区的 DO 标记和 alarm 在第一次 R2 写入之前持久化。仓库忙碌时 alarm 立即安排 30 秒后重试并返回；空闲时才加入串行队列进行清理，不能回收仍在接收的上传，也不让 alarm 的 15 分钟预算消耗在等待 HTTP 请求上。请求结束先删除最多 1,000 个临时键；剩余键交给 alarm 分页回收，只有删完该会话后才移除标记。进程中断或清理失败仍保留恢复依据。待清理会话达到八个时拒绝新导入并重新安排回收，限制积压。删除仓库也会清理其临时对象和标记。

## 明确的应用预算

| 项目                              | 预算                                               |
| --------------------------------- | -------------------------------------------------- |
| 一次原生 receive 请求（含命令头） | 64 MiB                                             |
| 一个 pack 的条目                  | 25,000                                             |
| 展开总量（含 delta 指令及结果）   | 256 MiB                                            |
| 单对象 / delta 深度               | 8 MiB / 64                                         |
| 单次解析输入片段                  | 16 KiB                                             |
| R2 压缩输入块                     | 4 MiB，按需读取                                    |
| BYOB 读取缓冲                     | 64 KiB                                             |
| 正式 ObjectStore 的 LRU           | 8 MiB、最多 1,024 项                               |
| 正式对象待写队列                  | 不超过 8 MiB，最多四条并发写入；其他写入仍默认两条 |

原生请求优先使用 BYOB；不支持时普通 reader 的单块输入最多 1 MiB。没有可读进展的等待超过 20 秒则终止；处理当前对象的 R2 等待不算输入空闲时间。以上为应用预算，云端仍受账户请求体、CPU、内存和子请求限制约束。见 Cloudflare [Workers 限制](https://developers.cloudflare.com/workers/platform/limits/) 和 [Durable Objects 限制](https://developers.cloudflare.com/durable-objects/platform/limits/)。

`peakPayloadBytes` 是解析阶段当前对象（或基对象、delta、输出之和）的最大字节数；`peakStagedBytes` 和 `peakCachedBytes` 分别来自正式 ObjectStore 与临时块存储。它们不是 V8 堆总量：规范化编码、哈希、压缩器和运行时还有临时分配。日志只记录仓库 UUID、字节、数量、I/O 指标与 BYOB 状态，不记录用户文件内容或凭据。

上游同步客户端的旧缓冲解析器、Fork 的暂存、归档及历史等算法保留各自限额。原生流式 receive 的新预算不会自动放宽这些路径，也不表示已验证 25,000 条目/256 MiB 极限下的生产吞吐。

## 验收

类型检查和 182 项单元测试通过，覆盖任意分块、前向 REF/OFS_DELTA、深度/展开/传输预算、外部基对象异常、临时数据篡改、校验和与截断、R2 写入失败、陈旧/禁止引用、分页回收、有界四路写入排空、忙碌 alarm 延后，以及已持久化元数据的完整对象图验证。

最终本地核心回归通过 43 次 API 断言及原生 Git/LFS 等检查。`npm run test:receive-scale` 在隔离私有空间中，一次推送 2,100 个小文件和五个 7 MiB 随机文件，得到 2,108 个对象和约 35 MiB 的 pack。35 项本地 Git/HTTP 检查通过，首次推送约 3.9 秒，两个协议的克隆均约 1.7 秒；这是模拟器结果，不作为云端性能结论。

生产同规格验收通过 33 项 Git/HTTP 检查，包括原生 v0/v2 克隆、增量推送/获取、`fsck --full --strict`、分支一致性、匿名私有访问拒绝，以及中断下载后再次访问仓库。生产 pack 为 36,818,954 字节，原始随机文件内容共 35 MiB。

| 生产操作      |   本次耗时 |
| ------------- | ---------: |
| 单次首次 push | 724,553 ms |
| v2 全量 clone | 330,094 ms |
| v0 全量 clone | 159,425 ms |
| 后续增量 push |   7,424 ms |
| v2 增量 fetch |   3,672 ms |
| v0 增量 fetch |   2,339 ms |

入站使用 9 个压缩输入块，临时对象合并成 8 个块。临时块读取/写入各 8 次，正式对象写入 2,108 次，引用验证额外读取 R2 1 次。HTTP 输入块峰值 8 KiB；解析 payload 峰值 7 MiB；临时块缓存及正式待写批次峰值均约 7 MiB。这些指标不包括整个 isolate 的堆和运行时分配。

两次全量克隆分别读取 R2 2,107/2,108 次，预取峰值均为 7,340,083 字节、4 个对象。两个增量 fetch 命中缓存，R2 读取为零。中断下载的已开始 I/O 排空后，`ls-remote` 在 30 秒验收门槛内完成。上述时间是本次样本，冷克隆和首次导入的吞吐仍明显需要优化。

生产普通写入专项另通过 57 次协议/HTTP 断言（含轮询）：八次提交 API 写入、两个客户端争抢同一预期引用、陈旧引用重试拒绝、两次原生增量推送、版本化 DAG 触发及 clone/fsck。它与大导入在不同的隔离仓库中并行完成。两组生产验收均已结束，测试仓库、空间及本地 Git 夹具已清理；使用用户原有令牌时不撤销该令牌。

## 本轮发现并修正的问题

第一版直接逐对象读取 HTTP 流并写入临时区。首次生产导入约 33 秒后收到 HTTP 502，日志记录请求取消，当时接收约 68 KiB、写入 652 个临时对象，未发布引用。现存记录不能确定提供方取消的内部原因。后续改为先分块暂存压缩输入，减少细粒度 R2 写入对上传连接的阻塞。

第二版完整暂存了 9 个输入块，但逐对象暂存持续较久。遥测显示等待仓库队列的 alarm 达到 900 秒墙钟限制，同次上传也报告 `exceededWallTime` 并返回 500。最终实现合并临时对象、延后忙碌 alarm、使用有界四路正式写入并复用已持久化对象元数据；随后通过上述云端验收。失败夹具已清理，并通过 R2 元数据确认第二次测试前缀为空。

本版本没有改变正式 R2 对象键或数据库表结构。永久对象集中存储、完整 pack 缓存、同仓库读取并发及大型 Fork/历史算法仍属于后续目标，详见 [性能计划](GIT-SCALE-PLAN.md)。完整 GitLab/Gogs 总目标仍在进行。
