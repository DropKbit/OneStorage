# v0.18 传输期间的页面读取

原来的仓库队列一直等待 Git HTTP 响应发送完毕，导致目录、文件和提交页面在长时间上传或下载期间也排队。本版保留 Git 主操作的串行屏障，额外提供有界的只读快照通道。它读取仓库已经持久化的引用和不可变对象，不执行引用发布、共享 SQL 索引更新或 pack 缓存回收。

## 调度与一致性

- 主操作仍然逐个执行，并等待流结束、取消与已开始 I/O 的排空。Git 写入互相保持串行，两个完整 clone 仍受原来的主队列约束。
- 完成旧数据迁移及请求初始化后，原生 Git 上传/下载和选定的 GET 可以开放快照通道。目录、文件、分支、标签、提交列表/详情以及原始文件条件请求复用同一套读取实现。
- 每个响应使用自己捕获的普通或 ephemeral 引用集合。命名分支在读取中更新时，目录和 README 仍来自同一提交。项目版本不匹配返回 409，删除状态返回 404；读取不得用缓存跳过这些检查。
- 生命周期、同步、Fork 和其他未开放的操作保持排他。排他请求入队即停止后续请求进入快照通道，并在开始前等待已有快照响应排空，因此不能让归档、转移、默认分支修改或删除越过在途读取。
- 外层 Worker 继续进行当前用户、令牌、空间和项目权限检查。角色或令牌撤销后的新请求重新鉴权；本版不改变已获授权的在途请求语义。
- 未出现在该命名空间当前引用头部的显式 SHA、短 SHA 和祖先选择器走原路径，避免并发通道提前访问尚未发布的对象；这些选择器的既有 API 能力仍保留。

Cloudflare 的异步 I/O 会允许请求交错，默认存储 input/output gates 不能替代应用对整次传输的约束。实现依据 [Durable Objects 规则](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/)，不在长网络操作外包裹 `blockConcurrencyWhile`。

## 额外资源预算与回退

同一 isolate 可能容纳多个仓库 DO，因此额外快照槽在 isolate 范围只允许一个活动响应。每仓库最多排入四个快照请求，总请求排队上限仍为 16。主操作本身的既有资源预算不由这个槽替代。

快照对象上限为 256 KiB，每次响应最多 64 次对象访问、累计返回给读取算法的对象数据不超过 1 MiB。即使命中对象缓存也计费；并发访问先预留字节，缓存中的大对象不会先复制再拒绝，R2 大对象在消费 body 前退回原路径。快照不使用共享可达索引，因此不会与主写入的索引构建竞争。

缓冲响应最多 2 MiB，保留状态码、Range/HEAD/条件读取语义。预算不足、项目版本缓存需要刷新或 isolate 快照槽正忙时，等待已开始读取结束，再重新进入主队列；不会向用户增加新的文件大小拒绝。这里限制的是数据与调度规模，不宣称这些数字是整个 V8 堆的峰值。

快照响应仍有 20 秒空闲期限。只有响应结束、取消或出错且所有已开始的读取都结束之后，才释放槽。`X-OneStorage-Read-Mode: snapshot` 表示该响应使用并发通道，可用于验收；它不授予任何访问权限。

## 验收

`npm run test:read-concurrency` 先发布一个含 README 的种子提交，再上传 10 MiB / 1,105 个新对象，仓库总计 1,108 个对象。在原生 push 尚未结束时读取种子提交的目录和 README，确认匿名拒绝，并提交归档请求，验证 push 完成后才归档。恢复后暂停出站 Git 响应并查看目录，再执行增量 push/fetch、原生 v0/v2 clone 和严格 fsck。本地还保留暂停在 pack header 的入站请求及归档顺序测试，最终清理所有夹具。

单元测试覆盖调度顺序、快照与主写入并存、生命周期等待、预算回退无死锁、错误/取消排空、isolate 槽、缓存命中字节计量和真实 Repository 的版本/快照前置检查。类型检查和 208 项单元测试通过。原始本地传输专项通过 57 项检查；扩展到种子提交与真实原生上传后通过 68 项检查，均核对 snapshot 响应标记与引用一致性。核心回归另有 43 次 API 断言及原生 Git/LFS 等检查通过，归档专项 63 项、转移专项 79 项通过。生产扩展专项通过 57 项检查（不包含本地的人工入站暂停探针）；生产写入与版本化流水线回归通过 43 次断言。

生产夹具含 1,108 个对象、10 MiB 随机负载。真实原生大包 push 用时 74.5 秒；期间读取已发布种子提交，7.22 秒内观察到 snapshot 响应（包括轮询和网络时间），目录与 README 引用一致，且 push 尚未结束。已排队的归档等待约 66.7 秒后成功，恢复后暂停下载时快照读取用时 767 毫秒。首次 v2 clone 为 41.8 秒，随后 v0/v2 缓存 clone 为 3.74/3.26 秒；增量 push 后首次 clone 27.5 秒，缓存 clone 7.59 秒。所有原生 clone/fetch 均通过严格 fsck。测试仓库和空间清理完成，独立 R2 前缀列表确认空。上传与下载期间的两次快照诊断均无 R2 写入。

这些是单次端到端验收数据，不是延迟保证，也不能据此宣称大包上传和无缓存克隆已经足够快。

## 仍需完成

完整 GitLab/Gogs 目标保持有效。首次导入、无缓存 clone、多个完整 Git 传输并发、大历史遍历及复杂 diff/搜索仍需继续优化；本版不等于所有页面都消除了等待。完整 CI/CD、身份集成和协作功能继续见 [ROADMAP](ROADMAP.md)。

## 生产探针修正记录

首轮生产测试通过下载暂停时的目录读取（957 毫秒），但人工暂停小型入站请求正文时，八次浏览请求均没有 snapshot 标记，专项因此失败并完成清理。该 receive 请求最终在清理阶段返回 404，未获得暂停正文期间在 DO 内重叠执行的证据；不能把它计为通过的上传并发验收。

随后用不修改引用的固定长度四字节 Git 空请求复查：暂停正文时四次目录读取均无 snapshot 标记，释放后空请求返回 200。应用源码没有在 Git 路由预先消费整个正文；现有证据不足以把延迟归因到具体网络组件。线上改用真实原生 Git 大包的 R2 保存阶段作为重叠窗口，并等待所有已开始请求完成后才清理，避免清理与晚到请求竞争。本地仍验证人工暂停正文的情况。
