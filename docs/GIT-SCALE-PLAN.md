# 大仓库能力：尚未完成的核心目标

v0.8 提交 d80a1b7 的源项目可达图实测为 408 个对象、4794833 字节展开内容。它通过验证不代表大型 GitLab 项目已经可用。

v0.8 时的 `ObjectStore` 是单次操作缓存，最多 32 MiB。`GitRepository.updates` 会遍历新 refs 的完整对象图，`validateFetch` 会遍历全部 refs；上传协议随后还会遍历 haves、wants 与标签。5000 对象图限额因此会限制长历史/大仓库，不能只通过提高常量来解决。

后续开发必须实现并验证：

1. 仓库隔离的持久化对象/边索引，只有类型、哈希及可达闭包验证完成后才标记可信。未发布上传、失败推送或跨 Fork 未公开分支不能通过索引变成可下载内容。
2. 推送按新对象与已验证边界增量校验；将索引与 refs 的一致性纳入 DO 原子发布或可恢复协议。部分 R2 写入、数据库失败、Worker 重启和并发引用变更都不能产生指向不完整对象图的引用。
3. fetch/clone 的可达集合规划及 pack 输出不把整个仓库保留在内存；支持流式校验和、压缩、背压与客户端断开，维持 Git v0/v2、delta、标签、Notes 和临时引用隔离。
4. 旧仓库索引可恢复地建立，并保留 SHA/类型/碰撞校验。关联的 fork、归档、blame、CODEOWNERS 和合并关闭 Issue 需要分别审视全历史遍历，不能只优化一个 clone 路由。
5. 在超过旧 5000 对象/32 MiB 门槛的真实原生 Git 仓库上验收 clone/fetch/push/fsck，记录冷/热缓存、峰值内存、R2 读写量、故障恢复和私有对象隔离。保留每次操作/对象的明确限额，但不把该限额当作整个仓库容量。

v0.12 已加入仓库 DO 持久闭包索引、有界读取缓存、流式出站 pack 与公共 have 协商，参见 [实现及剩余边界](GIT-SCALE-v12.md)。真实 5,424 对象、42 MiB 数据已在本地原生 Git 跨过旧下载上限；这不替代流式大导入、大 Fork、全部历史算法及更大规模生产验收。此项仍在持续能力矩阵中。

## 下一阶段的性能验收

v0.12 生产 v2 冷克隆实测 640,543 毫秒，5,423 次 R2 读取、44,365,169 字节；对象缓存峰值 7,546,745 字节。该结果验证流式路径的可用性，同时暴露逐对象串行 I/O 的延迟。下一阶段首先用同规格数据建立前后对比：

1. 根据已验证索引中的对象大小安排有界预取，同时限制对象数与总预取字节。不能仅把串行读取改成无界 `Promise.all`；必须计算当前对象、预取、哈希输入、共享缓存及压缩状态的总内存预算。取消或失败必须停止继续排队，并排空已开始的 I/O。
2. 设计不可变对象的合并存储或完整 pack 缓存，降低每次冷克隆的 R2 操作数。缓存键包含仓库 UUID、准确的对象选择及协议选项；当前用户的 refs 可见性仍在缓存读取前验证，不能因缓存命中暴露隐藏分支。
3. 单独测量下载期间同仓库页面、fetch 与写入的等待时间。目前响应流持有仓库队列，慢下载会让后续仓库引擎操作排队。若引入快照读取或读租约，必须重新验证归档、转移、删除的确认语义、权限版本、取消和 GC，不能直接移除现有屏障。
4. 流式入站解析与 delta 暂存解决单次首次导入的 16 MiB/2,000 对象限制。必须覆盖超限、中断、缺失基对象、R2 写入失败和最终 pack 校验和失败，确保 refs 不推进。

Cloudflare 当前对每次调用同时等待响应头的连接数限制为六，包含 R2；响应头到达后的连接不再计入该限制。预取调度还应保留应用其他 I/O 的余量。参见 [Workers 连接限制](https://developers.cloudflare.com/workers/platform/limits/#simultaneous-open-connections)。上述第 1 项已在 v0.13 实现并验证，见 [有界预取记录](GIT-PREFETCH-v13.md)；第 2–3 项仍待完成；第 4 项的 v0.16 进展见下节。

## v0.16 进展与永久对象集中存储的约束

流式入站、R2 临时块、DO 清理恢复和成功写入后的有界元数据复用见 [入站记录](GIT-RECEIVE-v16.md)。第 4 项的入站实现已完成，生产规模与剩余边界以该记录为准。v0.16 正式对象仍使用原有不可变 R2 键，没有迁移永久存储格式；逐对象正式写入、冷克隆请求数量和同仓库排队仍需继续优化。

集中存储不能仅改仓库主路由。当前源码有以下 ObjectStore 构造路径，下一阶段必须保持一致读取：

| 路径                         | 用途与约束                                                             |
| ---------------------------- | ---------------------------------------------------------------------- |
| `src/repository.ts` 主请求   | 本仓库 DO 索引与共享对象缓存，仍验证当前可见 refs                      |
| `src/repository.ts` 后台同步 | alarm 恢复路径创建独立对象存储，不应依赖前台请求的缓存                 |
| `src/lifecycle.ts`           | 源 DO 向已保留的 Fork 目标复制对象，涉及另一个仓库 UUID                |
| `src/fork-reviews.ts`        | 导入贡献时读取源 Fork，并写入目标仓库，必须维持贡献授权和对象快照      |
| `src/review.ts`              | 没有现成 ObjectStore 时读取 CODEOWNERS，不能因存储格式变化绕过审阅门禁 |

后续方案需要明确：旧松散对象与新块的混合读取、定位元数据的持久化位置、跨 DO 的授权和死锁约束、缓存总字节预算，以及旧版本回滚能否读取新数据。R2 块和定位信息必须先于 refs 持久化；失败时保留旧引用并能回收孤立块，不能仅凭一个定位记录授权下载。

验收应包含首次导入、冷/热 clone、重复内容与增量 push、Fork 和跨 Fork MR、CODEOWNERS、归档/转移/删除、备份恢复及 Worker 重启。另需限制深层或宽树遍历的活动边数量，分别测试元数据与字节缓存的总预算。以真实云端请求数、耗时、完整性和权限验证共同评估，不能仅用本地模拟器速度判断完成。

优先评估可丢弃的完整 pack 缓存，以保持当前松散对象格式及跨 Fork 读取的兼容性。缓存必须绑定仓库 UUID、准确的可见对象集合和协议选择，在鉴权及可达集合计算之后使用；不能直接复用包含额外未引用对象或外部 delta 基对象的入站薄包。成功写入缓存之前不发布缓存描述，缓存缺失或损坏应能回退到正式对象路径；保留容量、失效和回收边界，并比较首次与增量推送后的冷/热克隆。

读取并发应作为独立变更：普通推送可以与不可变对象快照读取并行，但归档、转移、删除和权限变更的确认语义必须明确。若用读取租约代替整个响应持有队列，应验证取消、已开始 I/O 的排空、缓存总量和旧权限快照的处理，再放宽当前串行屏障。

v0.17 已实现上述可丢弃完整 pack 缓存路径，具体边界与验收见 [GIT-PACK-CACHE-v17](GIT-PACK-CACHE-v17.md)。后续优先验证读租约和同实例总预算，再扩展永久 packed 对象读取，不能因热 clone 加速就声称首次导入或并发目标完成。
