# 项目归档与转移：后续实现门槛

目标保持完整。v0.10 已实现可恢复归档及实际 Git/D1/CI 写屏障，契约见 [项目归档](ARCHIVE-v10.md)；下一阶段实现转移，不能用仅修改 namespace 的方案宣称完成。

- 归档要同时冻结原生 Git/REST/临时引用/LFS、Issue/MR/Wiki/发布等写入，停止同步和新 CI，并使正在执行的 Runner 失去发布资格。读取、clone、导出仍可用；应用发布状态需要明确处理。
- DO 的持久化状态应拒绝已通过外层鉴权、却在归档后才进入队列的 Git 请求。D1 事务或约束也要防止协作元数据在归档后继续写入。后台补偿、GC、取消任务必须仍能运行。
- 转移保留仓库 UUID、R2 内容、Issues、MR、Wiki、发布等项目数据；重新计算目标空间继承权限。要求源所有权和目标空间授权，冲突名称不能部分迁移。
- 转移后，旧命名空间的令牌策略和在途写入不得继续获得旧权限；需要项目权限版本校验。旧路径跳转必须重新授权，不能泄露私人目的地。
- 连接、Webhook、CI 凭据和托管应用的归属应与转移契约一致；同一 D1 事务内处理归属、审计与访问状态，避免只迁移网页名称。
- 验收要覆盖真实 Git、LFS、CI/Runner、后台同步、跨空间权限与并发请求；生产只能操作隔离测试项目，保留 `1shk/nb` 和 Cubelink 的地址。
