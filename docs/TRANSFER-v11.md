# 项目转移与重命名（v0.11）

在项目设置中展开「转移或重命名项目」，填写目标空间和项目名。要求源项目 owner；目标必须是操作者本人的个人空间，或其拥有 owner 权限的团队空间。管理员身份不绕过项目所有权。读取/写入 PAT 仍服从项目角色，只读 PAT 和委托 JWT 不能转移项目。

API：`POST /api/repos/{namespace}/{repo}/transfer`，正文 `{ "namespace": "team", "name": "project", "revision": 0 }`。名称可省略，沿用当前项目名；revision 来自项目详情的 lifecycle_revision。响应是最新项目元数据，包括不变的 UUID 和递增后的版本。

## 保留与交接

- Git 引用、R2 对象、临时引用、LFS、Issue/评论/标签/看板、MR/审阅、分支保护、Wiki 历史、Release、CI 历史/产物及部署版本沿用原项目 UUID，不搬运或复制对象。
- 显式项目成员保留；原团队的继承成员不再获得权限，目标团队按当前成员角色获得权限。公开/私有状态及归档状态不变。归档项目可以直接转移，仍保持只读。
- 跨空间转移取消 queued/running CI 并清除租约，取消 pending 同步，撤销 Runner 与 Git 连接凭据，删除 Webhook 配置及其投递记录，清除上游连接，关闭自动流水线和环境公开访问。历史 CI 与部署对象保留。已经发出的 HTTP 请求无法撤回；转移后的新事件不会使用旧连接。
- 新空间须重新配置连接并明确启用流水线/应用；旧 Runner 凭据不能重新领取任务。个人 PAT 和签名 API key 不会被全局撤销，但访问新地址必须通过当前项目权限及 JWT 路径限制。
- 同空间重命名保留连接、运行任务、自动流水线与公开应用；同步任务更新到新项目版本。Git URL 改变，应用 UUID URL 不变。
- 正在初始化或等待确认上游写入结果时返回 409，须先完成恢复。待补偿的已发布合并先完成 D1 投影。

## 历史地址

旧路径按 UUID 直接解析到当前项目，不产生多次转移的跳转链。当前有权限的网页/API GET 收到 307，前端替换历史地址；API 写请求需使用新地址。原生 Git 客户端可能在跟随发现请求跳转后仍向原始 URL POST，因此 Git/LFS 的后续请求会在重新授权后继续处理。

授权使用目标的当前空间角色与 JWT 路径限制；失去权限的原空间成员不能利用别名读取或推送。未授权请求不返回私人目标 Location。历史路径不能被另一个仓库抢占；项目可转回自己的历史路径。删除项目并完成 GC 后清理别名。

## 读写一致性

转移由仓库 Durable Object 串行队列排序。D1 同一事务复查源/目标所有权、目标名称冲突、版本、连接处理、项目归属与审计，任一失败均回滚。

仓库路由取得授权快照后，使用仅限当前请求的 D1 包装器；写语句与 lifecycle_revision 检查在一个 batch 事务执行，包含 `RETURNING` 和已有业务 batch。普通 SELECT 与版本检查放在同一个只读 batch 快照中，不新增写事务；转移前授权的请求不能在转移后查询新空间的数据。后台 Webhook outbox 调度使用原始绑定，避免把某个请求的项目版本绑定到其他项目的投递。新仓库写路由必须通过 repoAccess 获取此快照；不要用共享环境对象存放请求状态。

Git/LFS 和其他经 DO 处理的请求携带版本，在进入串行队列后检查持久版本缓存，包括 GET/HEAD。转移或归档前先持久化失效标记，D1 完成后更新版本；提交后缓存写入失败时，后续请求必须先从 D1 恢复版本，恢复失败则拒绝读取。旧空间授权的排队读写不能在转移后继续执行，正常缓存命中不增加 D1 查询。上游任务也携带版本，迟到结果不能重新激活已取消的同步。

D1 batch 与返回行行为依据 [D1 事务批处理](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch) 及 [prepared statements](https://developers.cloudflare.com/d1/worker-api/prepared-statements/)；协议、角色隔离、原子回滚及原生 Git 行为同时由项目自身验收覆盖。
