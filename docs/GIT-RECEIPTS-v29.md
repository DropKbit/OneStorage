# Git 提交与持久审计

**简体中文** · [English](en/GIT-RECEIPTS-v29.md)

v0.28 的源码推送曾返回 HTTP 500，但随后的 `ls-remote` 和独立镜像 `fsck --strict` 确认引用及对象已完整写入，对应审计记录没有出现。历史 Observability 查询被当前 Wrangler 凭据拒绝，三次隔离云端推送及过滤后的实时日志均未复现，因此**这次历史异常的具体原因尚未证实**。

故障注入确认了旧代码中的一个独立缺陷：主 Worker 收到成功的 Git Durable Object 响应之后还会同步写入 D1 审计；此时 D1 写入失败，外层就用 HTTP 500 替换已经成功的 Git 响应。v0.29 移除这条提交后的审计依赖，并确保审计意图先与引用一起落盘。

## 原子发布与恢复

每个原生 HTTP receive-pack 请求若实际修改了引用，在同一次 DO 存储事务内保存引用、原有的逐引用 push 事件和一个 `git-receipt:` 记录。记录包含随机事件 UUID、项目 UUID、通过鉴权的用户 ID、时间和实际修改引用数量。用户 ID 由主 Worker 从当前身份生成，外部同名请求头无法替换它。一次多引用事务只产生一个审计记录；没有引用变更的空操作、保护规则拒绝和失效旧引用不会被记作成功发布。

发布前仍先保存并验证 R2 Git 对象及闭包。审计不在成功的 DO 响应之后另行写入 D1。需要超过 128 个存储键时，以每批最多 128 个键在一个 DO 事务中提交，避免新增审计键破坏大批分支/标签更新的原子性。所有存储写入保留默认确认行为，不使用 `allowUnconfirmed`。

DO alarm 每轮优先投递至多 20 个记录。首次外部 I/O 前先设置 30 秒后的恢复 alarm，只有 D1 确认后才删除持久记录。D1 提交响应丢失或 DO 删除标记失败时会重试；`audit.event_id` 的唯一索引使同一事件只插入一次，已有的通知触发器也只触发一次。成功投递后仍有待处理记录时继续处理；失败保留记录并安排恢复，已有 CI、webhook 和同步处理仍保留。

每个仓库最多积压 512 个未投递的原生 Git 审计记录。达到上限时，在接收入站 pack 和可能的上游转发之前拒绝新的原生写入，并在引用实际发布前再次检查。这个上限用于阻止长期依赖故障导致无限积压，不删除尚未投递的记录。

## 审计接口和兼容性

现有 `GET /api/repos/:namespace/:repo/audit` 增加可空的 `event_id`。旧记录及其他审计动作保持 `null`；新的原生 Git 成功发布动作仍是 `git.receive_pack`，`detail` 是包含 `refs_updated` 的 JSON。时间采用实际引用发布时记录的时间，而非后续重试时间。

审计页面/API 的权限不变。新审计为异步可见，不能要求 push 返回时 D1 页面已经显示该记录。账户随后被禁用不抹去历史行为；已删除账户允许空 actor；项目转移后仍按项目 UUID 投递。删除整个项目仍按原有垃圾回收规则删除其审计及待处理记录。

部署需先应用 `0023_git_receipts.sql`。它只为现有 audit 表增加可空列和唯一索引，旧 Worker 在过渡期仍能写入原有记录。本功能不会为旧版本未持久化的缺失审计凭空补造记录，也不将旧请求的同步审计视为新投递机制的事件。

## 边界与验证

这解决了已复现的「成功 Git 响应被后续审计失败替换」路径，并为已接受的原生引用变更保留持久审计意图。它不保证网络、平台或存储永远不返回错误，也不证明 v0.28 历史 500 一定由审计引起。主 Worker 到 DO 的调用若抛出未确认的传输错误，现返回带 incident ID 的 503，并记录独立的 gateway-receive 诊断；不把它误报成确定回滚，也不输出提供方原始消息或凭据。已有 DO 错误响应和 Git report-status 保持原样。客户端遇到不确定结果仍须先检查远端引用，不得盲目重放写入。其他 HTTP Git 编辑 API 的审计、上游同步的外部提交确认及其余可靠性工作另行推进。

测试覆盖提交后 D1 故障、投递恢复、D1 不确定提交、DO 标记删除失败、通知去重、事务失败/积压拒绝、历史身份、批量处理和大批存储的原子回滚。`npm run test:git-receipts` 使用真实原生 Git push、原子创建/删除 2 个及 129 个引用、空操作、受保护分支拒绝、异步审计、镜像与严格 fsck 验证；退出前清理临时仓库及凭据。

存储行为依据 Cloudflare 官方 [SQLite-backed DO Storage](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/) 的原子方法、128 键限制、事务及默认写入确认语义。
